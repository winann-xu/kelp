## 1. 网关模式（FR3）

### 1.1 交付物
`scripts/gateway-mode.sh` —— 幂等脚本，动作与保证：

| 动作 | 说明 |
|---|---|
| 记录原值 | 首次 apply 时把 `ip_forward`、FORWARD 默认策略写入 `/etc/kelp/gateway-originals.json`，供回滚精确还原 |
| 开启转发 | `sysctl net.ipv4.ip_forward=1` + 落 `/etc/sysctl.d/99-kelp-gateway.conf`（重启仍生效） |
| FORWARD 放行 | 仅针对 `ens160 ↔ tun0`（+ 自测 veth）插入带 `KELP-GATEWAY` 注释的 ACCEPT 规则；用 `iptables -C` 判重，重复执行不产生重复规则 |
| 开机自恢复 | `kelp-gateway.service`（oneshot）开机重放规则 |
| 自测 | 用**网络命名空间**模拟一台【未装 EasyTier 客户端】的设备（IP 192.168.50.241/24，网关指向本机），测试访问 B 站点 `https://192.168.1.99:5667/` |

### 1.2 执行方式（需 root，在 192.168.50.9 上）
```bash
sudo bash /tmp/kelp-gateway.sh apply      # 开启 + 前后自测
sudo bash /tmp/kelp-gateway.sh status     # 只读查看
sudo bash /tmp/kelp-gateway.sh rollback   # 回滚（恢复 ip_forward 原值 + 删规则）
```

### 1.3 首轮自测暴露的问题与根因（2026-09-19 23:2x）

50.9 首次 apply 的自测结果：**ping 通、HTTPS 000（不通）**。为定位，助手在**公网节点上用网络命名空间造了一台免客户端设备**逐层复现（脚本 `scripts/diag-mtu-forwarding.sh`），结论链如下：

| 候选修法 | 结果 |
|---|---|
| 仅开启转发（`ip_forward=1` + FORWARD 放行） | 小包/大包 ping 通，**TCP 握手不通、HTTPS 失败** |
| + MSS 钳制（`TCPMSS --clamp-mss-to-pmtu`） | 仍不通 |
| + TCP 校验和填充（`CHECKSUM --checksum-fill`，TCP/UDP 都试） | 仍不通 |
| **+ SNAT（`-t nat POSTROUTING -s 192.168.50.0/24 -o tun0 -j MASQUERADE`）** | **TCP 握手通、HTTPS 200**，页面标题 `飞牛 fnOS`；A 站点 `https://192.168.50.9/` 返回 401 ✅ |

**根因**：转发报文的源地址是内网私网地址（如 192.168.50.241），异地站点没有它的回程路由 → TCP 全部石沉大海。**ICMP 能通是假象**（EasyTier 对代理网段会自行代答 ping），不能作为"通路已好"的判据——这一点已写入排查准则。
**修法**：网关机对"从内网接口进入、经 tun 出去"的流量做 SNAT（源改写成网关机自己的组网 IP）。代价：对端看到的是网关机地址，看不到终端真实 IP（与主流组网软件的网关模式一致）。
MSS 钳制仍保留（隧道 MTU 1360 < 内网 1500，防大包被丢，属防御性设置）。

脚本已更新：`add_rules` 现在同时下发 ①FORWARD 放行 ②SNAT ③MSS 钳制；`del_rules`/`rollback` 精确删除这三类规则（计数含 filter/mangle/nat 三张表）。

### 1.4 首轮"仍不通"的真正原因：50.9 上的代理环境变量（假失败）⭐⭐⭐

修好 SNAT 后仍报 `HTTPS 000`。深挖发现 **50.9 上设了全局代理环境变量**：

```
http_proxy/https_proxy/HTTP_PROXY/HTTPS_PROXY = http://192.168.50.12:10809
no_proxy/NO_PROXY = localhost,127.0.0.1,192.168.50.0/24      （写在 /etc/environment、/etc/profile.d/proxy.sh、~/.bashrc）
```

于是 50.9 上**任何 curl**（包括我们的自测、以及访问公网面板）都被塞进这个代理；而该代理**本身不通**（经它访问 baidu 也是 000，直连 200）。判据对照：

| 目标 | 带代理 | 绕代理（`--noproxy '*'`） |
|---|---|---|
| 公网面板 `https://47.116.73.216:18080/` | 000 | **401**（正常，需鉴权） |
| B 站点 `https://192.168.1.99:5667/` | 000 | **200** |
| A 站点 `https://192.168.50.9/` | 000 | **401** |

结论：**"curl 000"在这台机器上不代表网络不通**。脚本已改为所有 curl 加 `--noproxy '*'`，并在检测到代理变量时打印提示。
副作用提醒：这个代理也解释了 M1 时期"50.9 连 GitHub/ghfast 全部 000"的结论——当时很可能是同一个假象，而非真的被墙。

## 2. 流量护栏（FR7）

自建实现（不依赖阿里云控制台），落在只读面板里：

- 数据源：公网节点 `/proc/net/dev` 中所有非 `lo` 接口的**发出字节**（阿里云按出网流量计费，故只看 egress）

## 4. 重要实测更正：公网节点是硬单点（原假设被推翻）

任务书风险表原写“组网本身可 P2P，节点只是信令；节点宕机时已建立的连接仍可用”。**实测推翻**：

```
hub 停机 +0s : 邻居表中已无 kelp-50-9 ; https://192.168.50.9/ -> http=000
hub 停机 +3s : 同上
hub 停机 +8/15/25/40s : 同上（一直不通）
恢复 hub 后  : 15 秒内 2 条 P2P 自动重建
```

结论：**公网节点停止服务 → 整个组网立即中断**（含已在 P2P 直连的两台设备之间的流量），恢复后自动重连。影响：公网节点不可用期间，所有跨站点访问中断、面板不可用。

缓解选项（待用户决定，见任务书 D21）：
1. 接受（阿里云 ECS 稳定性高、故障自恢复；组网本身数据不经公网节点，恢复后不产生额外流量费）
2. 增加**第二个公网节点**（另一台 VPS，或异地低配实例）做信令冗余——成本最低的可靠性提升
3. 让节点额外连接 EasyTier 社区公共服务器作为备用信令——**需把网络名/密钥交给第三方**，隐私权衡，原则上不做

## 7. 运维要点：跨站点 P2P 回落中继（实测记录）

**现象**：公网节点多次重启后，NAS ↔ 50.9 由 `p2p/udp/21.5ms` 回落为 `relay(2)/31ms`；此时若两端有数据传输，将按 0.8 元/GB 计费。面板的红色中继横幅（M2 已实现）就是这条风险的探测器。

**本次已试**：等待 90s（无效）→ 重启 B 站点节点（无效）→ 触发跨站点流量（无效，lazy-p2p 未触发打洞）→ hub 侧 `--relay-all-peer-rpc true`（单独无效，参数保留）。
**修复手段**：两侧节点均带 `--need-p2p true` 并重启触发重新打洞（A 站点侧在 `/tmp/kelp-finish-50-9.sh` 中完成）。

**标准排查顺序**（面板出现"中继"时照此执行）：
```
1) 确认路径：easytier-cli peer | grep -E "relay|p2p"   （或看面板卡片徽章）
2) 触发一次跨站点流量：curl -sk https://192.168.50.9/  （lazy-p2p 场景下需要真实数据才会打洞）
3) 重启节点服务触发重新打洞：
   B 站点: docker restart kelp-b-node
   A 站点: sudo systemctl restart easytier-node
4) 确认两侧都有 --need-p2p true；hub 侧保留 --relay-all-peer-rpc true
5) 仍为 relay → 接受中继但立刻核对面板"今日出网"是否异常增长（0.8 元/GB）
```
